# Known gaps

These forms are still read differently than GitHub reads them. A gap can hide a rendered comment or expose an unrendered one. Each gap names the behavior and the evidence available for it: a GitHub probe, an oracle comparison, or a local parser check. A gap marked "Not probed on GitHub" is inferred from the implementation or the HTML standard and remains unconfirmed. Fix a gap only when a real document confirmed against GitHub needs it, following the tie-break in [CONTRIBUTING.md](../../CONTRIBUTING.md#principles).

- **Rendered text and other markup inside an open tag.** When raw HTML leaves a tag or attribute value open, the browser reads the rendered output that follows as part of it, until a character ends it. The scanner writes generated thematic breaks, code blocks, footnote markup, links, images, autolinks, and aligned cells, but still approximates or skips the other output listed in the [renderer audit](./generated-markup.md#renderer-output-audit). It misses:
  - **A `'` in rendered text,** which closes a single-quoted value. In `<div>\n<a b='\n\n'\n\n<!-- a -->old<!-- /a -->`, the lone `'` paragraph closes the value, so GitHub renders the marker, but the scanner keeps the value open and misses it. An image's `alt` text is written as empty, so a `'` in it is missed the same way. A scratch copy of the `tables` fragments with images, autolinks, and more aligned delimiter rows left 13 mismatches on seeds 7, 11, and 23 (20,000 documents each), and all 13 have this cause.
  - **Quotes in an ordered list's `<ol start="2">`.** In `<!-- a --><ol title="\n\n2. x\n\n<!-- b -->`, the oracle renders `b`, but the scanner misses it.
  - **Email autolinks,** which the autolink extension adds after inline parsing. In `<!-- a --><a title="\n\nx a@b.c\n\n<!-- b -->`, the oracle renders `b`, but the scanner misses it.
- **Tight lists.** A paragraph in a tight list renders without `<p>`, but the block phase assumes generated markup before every text block. When nothing else is generated there, an open tag or bogus comment from earlier raw HTML carries into the paragraph in the browser, while the scanner resets it. In `- <!-- n --><?x\n  text <!-- a -->old<!-- /a -->`, the `<?x` bogus comment hides `<!-- a -->` on GitHub, but the scanner reports it.
- **SVG and MathML context.** The [element stack](./html-tokenizer.md#github-html-handling) matches every numbered GitHub probe, but these cases are not modeled. Each can change whether a CDATA section hides the comments inside it. In the probes below, the markup follows `<div>\n` and precedes `<![CDATA[ > <!-- x -->KEEP ]]></div>`, as in the [element stack fuzz](./github-oracle.md#element-stack-fuzz). "Open" means GitHub kept the CDATA section as text, and "closed" means `<!-- x -->` was a comment. GitHub `/markdown` gave each result on 2026-11-17, the patched gumbo agrees, and the scanner reports the opposite. The fuzz groups 1, 2, 3, 7, 8, and 9 are a deliberate scope limit. Each needs a parser subsystem that the stack does not have, its code would add to the bundle for every user, and no real document has shown one: 0 of the 128 [corpus](./performance.md) files contain `<![CDATA[`, which every one of these gaps needs before it can change a report.
  - **The form element pointer (fuzz group 1).** A `form` start tag is ignored while a form is open, and `</form>` removes only the form, not the elements above it. `<form><svg></form>` is open, and `<math><ms><form><div></form>` is closed. An earlier probe, `<form><div><form></form><svg></form>`, also rendered the markers as text.
  - **`<template>` inside `<select>` (fuzz group 2)** is passed through, but its own insertion mode is not modeled, so tags inside it follow the select rules. `<select><template><svg>` is open, and `<select><template><keygen><svg></template>` is closed.
  - **Template contents (fuzz group 3).** Inside `template`, table parts open as in a table, and its mode ignores `</table>`. `<template><td><svg></td>` is closed, and `<table><template><svg></table>` is open.
  - **The table insertion modes (fuzz group 7),** such as a `td` start tag that closes an open cell, a `select` that a table part closes, foster parenting, and a `form` that a table pops at once. `<table><select><caption><svg>` and `<table><math><mi><form>` are open, and `<table><nobr><table><svg></nobr>` is closed. A table end tag that finds a foreign element of its name below an integration point is ignored, without a search for an HTML element of that name further below.
  - **A `nobr` start tag with an open `nobr` (fuzz group 8),** which the standard closes with the adoption agency algorithm and then reopens. `<math><mn><nobr><nobr></nobr>` and `<nobr><mtext><nobr><math></mtext>` are open. The same holds for an `a` start tag with an active `a`: `<a><a></a><svg></a>` rendered the markers as text.
  - **The adoption agency algorithm's furthest block (fuzz group 9).** The algorithm keeps a special element above the formatting element open, so an HTML element stays current. The scanner closes everything above the formatting element instead. `<svg><foreignObject><nobr><p></nobr>` and `<math><mtext><b><noscript></b>` are closed. This also differs after more than eight special elements, and the Noah's Ark clause compares names only, not attributes.
  - **`annotation-xml` with an HTML `encoding`** is an integration point in the standard, but the stack does not read attributes, so its children stay MathML. Not probed on GitHub.
  - **Reconstruction of formatting elements at text.** The scanner reopens popped formatting elements only at a start tag, not at the text before it, so a reopened element can land above a scope boundary that a browser would put it below. Not probed on GitHub.
  - **Raw `html`, `body`, and `head` start tags** are pushed as elements, while the standard ignores them. Not probed on GitHub.
  A tight-list paragraph, which renders without `<p>`, still gets a virtual `p`. GitHub's `/markdown` rendered both openers in `# <svg></h1>` followed by `<!-- a -->PRESERVE <![CDATA[ > <!-- a -->old ]]> tail<!-- /a -->` on 2026-11-14. The [foreign content tests](../../tests/specs/rendering/foreign-content.ts) check the resulting update; cmark-gfm and parse5 also show that an end tag for another heading level closes the heading. GitHub also rendered both openers when `| <svg></th>` precedes the same marker sequence in a table header. The same tests check this and body-cell and row closures against cmark-gfm and parse5.
- **A reference definition with a non-ASCII named entity near the expansion cap.** The [reference expansion budget](./reference-budget.md#reference-expansion-budget) charges a definition the decoded UTF-8 size of its cleaned destination and title. The [entity table](./reference-budget.md#reference-expansion-budget) holds only the names whose first decoded byte is ASCII, so a name that starts outside ASCII is charged its source bytes instead: `&eacute;` (8 source bytes, 2 decoded) costs 6 more, and `&nGt;` (5 source bytes, 6 decoded) costs 1 less. Near the cap, a lookup can then resolve where GitHub fails it, or fail where GitHub resolves it. That changes the report only for an image reference: a resolved image writes its label as `alt` text, so a comment in the label does not render, while a failed image renders the label as source text. A link renders its label either way. In the oracle on 2026-11-17, 99 uses of a 1,000-byte definition followed by `![<!-- a -->inner][s]` with a destination of 800 `u` characters followed by 100 `&eacute;` resolved, while the scanner rejected it and reported the extra `a` comment. The fast path is unaffected because it measures source bytes, and `&amp;` and `\&bne;` stay exact. The oracle fuzz output is byte-identical to develop, so no generated document crosses that boundary where the approximation changes a report, and the boundary tests use retained names. Not probed on GitHub.
- **Footnote labels with named entities that are not one ASCII byte.** The [entity table](./reference-budget.md#reference-expansion-budget) holds only the 49 names whose first decoded byte is ASCII, and a reference label accepts a named entity only when its value is one ASCII byte or `fjlig`. When a named entity in a reference label decodes outside ASCII or to more than one byte, such as `&eacute;` or `&bne;`, the scanner treats the reference as undefined. A definition that only such references use is then dropped, and its comments are not reported. An entity-shaped name the table does not hold, such as `&foo;`, is also treated as undefined. Before the trim, develop matched `[^&foo;]` literally, as cmark-gfm does; the trim changed this on purpose so that `[^&eacute;]` keeps its existing behavior. Not probed on GitHub.
