# HTML tokenizer and comment boundaries

The browser phase reads raw HTML the way GitHub's HTML parsing does. It decides where a comment starts and ends, which closers count, and whether a comment starts its line. This file records GitHub's departures from the HTML standard, the closer rules, and the line-start flag.

## GitHub HTML handling

**Decision: model GitHub's observed HTML parsing, not the HTML standard.** GitHub's `/markdown` API shows two departures from a browser that change which comments exist. The [GitHub probes](./github-oracle.md#github-probes) hold the evidence, checked on 2026-11-14. The [probe fixtures](./github-oracle.md#probe-fixtures) record the documents and GitHub's output for this section, including the later probes below.

- **Scripting is disabled.** `<noscript>` content is ordinary HTML, so its comments are comments. With tagfilter escaping the other raw-text elements, the browser phase has no raw-text state.
- **SVG and MathML never end at a start tag.** Inside `<svg>` or `<math>`, `<![CDATA[` starts a CDATA section, which is text until `]]>`. Outside them, it is a bogus comment that ends at `>`. The standard's breakout start tags, such as `<p>`, `<em>`, and `<font color>`, leave SVG in a browser but not on GitHub. End tags do close SVG: `</svg>`, and the end tag of any element open around the `<svg>`, including the `</p>`, `</li>`, and `</blockquote>` that the renderer writes.

The browser phase keeps one stack of open elements for the whole scan. Each raw start tag pushes its element, apart from HTML void elements and self-closing foreign tags. Void names inside foreign content are tracked as stack entries, including `br`: GitHub /markdown on 2026-11-15 showed that `<svg><br><svg></br></svg>` closes the foreign context, while an unmatched `</br>` in `<svg></br>` leaves it open (see the [foreign content tests](../../tests/specs/rendering/foreign-content.ts)). This is an effective stack model of those observations, not a claim about GitHub's internal element tree. Each raw end tag pops to the nearest open element with its name, unless the scope rules in the implicit close decision below stop it, and an end tag that matches nothing is ignored. An HTML heading end tag closes any heading level. An element is foreign when it is `<svg>` or `<math>` outside an open HTML `<select>`, which ignores both start tags, or when its parent is foreign and not an integration point. The renderer's own blocks push virtual entries, so their end closes what opened inside them: a paragraph pushes `p`, a list item `li`, a blockquote `blockquote`, a heading its `h1` to `h6` name, and tables their `table`, section, row, and cell elements. The block phase reports container opens and closes for this. Generated markup does not open or close a virtual entry when it is consumed by an unfinished tag or bogus comment, or when the tokenizer is inside a comment, a quoted attribute value, or a CDATA section. GitHub /markdown confirmed the unfinished-tag case on 2026-11-15; see the [foreign content tests](../../tests/specs/rendering/foreign-content.ts). The inline phase buffers label spans until link resolution and reports the generated `a` around them; resolved images discard their alt-text spans. GitHub `/markdown` rendered both marker openers for `[<svg>](u)` followed by `<!-- a -->PRESERVE <![CDATA[ > <!-- a -->old ]]> tail<!-- /a -->` on 2026-11-14, and the [link test](../../tests/specs/rendering/foreign-content.ts) checks the resulting update.

**Decision (2026-11-17): model integration points.** SVG `foreignObject`, `desc`, and `title`, and MathML `mi`, `mo`, `mn`, `ms`, and `mtext`, are the standard's [HTML integration points](https://html.spec.whatwg.org/multipage/parsing.html#html-integration-point). Their children are HTML, apart from `svg`, `math`, and, in MathML, `mglyph` and `malignmark`. In foreign content, an end tag closes the nearest element with its name above the nearest HTML element, as the patched gumbo decision below records. Any other end tag is processed as HTML, and it is ignored when its element is the nearest integration point or below it, because each point is a special element and a scope boundary. GitHub `/markdown` showed this on 2026-11-17. With `T` = `<![CDATA[<!--a-->old<!--b-->VIS]]>`, `<div>\n<svg><desc><b>x</desc>T</svg>\n</div>` rendered `<div>\n<b>xoldVIS]]&gt;\n</b></div>`: the `</desc>` was ignored, so `<![CDATA[` was a bogus comment and `<!--b-->` a comment. `foreignObject` and `mi` in the same place, and `<desc><b>xT`, gave the same result. `<desc>xT` after `</desc>`, `<desc>T`, `<desc><b>x</b></desc>T`, and `<g><b>x</g>T` rendered the markers as text, so `desc` itself is SVG, and `b` outside an integration point stays SVG, as GitHub has no breakout tags. The [foreign content tests](../../tests/specs/rendering/foreign-content.ts) lock these 8 cases. Each element keeps the positions of its foreign run's root, its nearest integration point, and its nearest HTML element, so each end tag is one comparison. `annotation-xml` with an HTML `encoding` is not modeled, because the stack does not read attributes.

**Decision (2026-11-17): model implicit closes, scope, and reopened formatting elements.** Without them, an element that a browser closed implicitly stayed on the stack, and a later end tag popped through an open `<svg>`, so the scanner reported CDATA text as comments. GitHub `/markdown` on 2026-11-17 showed which of the standard's [in-body rules](https://html.spec.whatwg.org/multipage/parsing.html#parsing-main-inbody) GitHub applies. Each probe was `<div>\n`, the markup, and `<![CDATA[ > <!-- x -->KEEP ]]></div>`: the markers render as text while the svg stays open. The modeled rules, all for HTML elements only:

- **Start tags that close a `p` in button scope:** the standard's list apart from `search` and `dialog`, which left `<p><search><svg></p>` and `<p><dialog><svg></p>` hiding the markers. GitHub's parser also treats `search` as not special and `</dialog>` as any other end tag, so it predates both.
- **Start tags that close their own kind:** `li` closes the nearest `li`, and `dd` or `dt` the nearest of either, unless a special element other than `address`, `div`, and `p` is above it. A heading closes a heading only when it is the current node: `<h1><span><h2></h2><svg></h1>` hid the markers. `button` closes a `button` in scope.
- **End tags respect scope.** `</p>` uses button scope, `</li>` list item scope, and other special elements default scope, whose boundaries include the integration points. `<div><button><svg></div>` hid the markers, so `button` bounds only `</p>`. Any other end tag, such as `</span>` or `</del>`, stops at a special element: `<span><div><svg></span>` and `~~a <div><svg>~~` kept them visible. Table end tags and `</template>` close through anything inside the table, as `<table><tr><td><object><svg></td>` showed, including integration points, as the patched gumbo decision below records. Table section and cell start tags are ignored outside a table: `<p><td><svg></p>` hid the markers, and `<span><td><svg></td>` kept them.
- **Formatting elements reopen.** A formatting element that an implied close popped stays in the [list of active formatting elements](https://html.spec.whatwg.org/multipage/parsing.html#list-of-active-formatting-elements), and the next start tag that reconstructs reopens it. `<p><b><div><svg></b>` and `*a <div><svg>*` hid the markers: the `b` and the paragraph's `em` reopened around the svg, and their end tag closed it. Without this, the p-closing rule would have broken them. An end tag of a formatting element is ignored when its element is out of scope and otherwise closes everything above it, which is where the [adoption agency algorithm](https://html.spec.whatwg.org/multipage/parsing.html#adoption-agency-algorithm) ends: `<b><div><svg></b>` hid the markers.

The renderer's virtual elements follow the same rules. A raw `div` inside a paragraph closes its `p`, so the paragraph's `</p>` finds none: `text <div><svg>` followed by a paragraph with the CDATA kept the markers visible, while `text <p><svg>`, a blockquote, and a tight list item, whose end tags still reach the svg, hid them. The [foreign content tests](../../tests/specs/rendering/foreign-content.ts) lock these cases. Each element keeps the positions of its nearest special element and scope boundaries, so each end tag is still one comparison. The list keeps at most three entries per name after its last marker, as the Noah's Ark clause does by name and attributes, so a reconstruction pushes at most 42 elements. That bound keeps the scan linear; an input that reconstructs 42 elements at every tag ran about 6 times slower than before this change, and `pnpm bench:ab` showed no output difference on its 135 inputs, with timing ratios from 0.98 to 1.05. The `a` and `nobr` start tags, which close an active element of their name, the form element pointer, the table insertion modes, and reconstruction at text are not modeled; see [known gaps](./known-gaps.md).

**Decision (2026-11-17): obsolete void elements.** The void set also holds the start tags that never stay open on GitHub. Each probe followed the implicit close probe form. `basefont`, `bgsound`, `keygen`, `frame`, `frameset`, `image`, `isindex`, `menuitem`, and `param` kept the markers visible after `<name><svg></name>` and hid them after `<span><name><svg></span>`, so the element was not open. `frame` and `frameset` are ignored in body, `image` becomes `img`, and `menuitem` and `isindex` follow older versions of the standard. `<nextid><svg></nextid>` hid them, so `nextid` is ordinary. The longest void name has 8 characters, which bounds the length fast path in `processElement`.

**Decision (2026-11-17): a foreign `select`.** A `select` inside svg is SVG, so it does not stop a later `<svg>` from opening: `<svg><select><foreignObject><i><svg>` kept the markers visible. An open HTML `select` already ignores `svg` and `math`, so no other check is needed. The [foreign content tests](../../tests/specs/rendering/foreign-content.ts) lock this probe.

**Decision (2026-11-17): `noscript` is special.** Scripting is disabled, so `noscript` content is HTML, and a comment inside it rendered as a comment. `<span><noscript><svg></span>` kept the markers visible, so `noscript` stops other end tags. It is not a scope boundary, as `<p><noscript><svg></p>` hid them, and its own end tag stops at a special element like any other end tag, as `<noscript><div><svg></noscript>` kept them visible. The [foreign content tests](../../tests/specs/rendering/foreign-content.ts) lock these probes.

**Decision (2026-11-17): the patched gumbo is the reference for the stack's rules.** The [element stack fuzz](./github-oracle.md#element-stack-fuzz) compares the stack with a gumbo patched to match GitHub, and GitHub `/markdown` agreed with that gumbo on all 32 probes of its mismatch groups and on 2 more for group 6. Where a group was an error in a rule that the stack already models, the stack now follows gumbo and GitHub. The [foreign content tests](../../tests/specs/rendering/foreign-content.ts) lock 2 or more probes for each group:

- **A foreign end tag reaches through integration points (group 5).** The standard's [foreign content steps](https://html.spec.whatwg.org/multipage/parsing.html#parsing-main-inforeign) walk every foreign element down to the nearest HTML element, and integration points are foreign. `<math><mtext><svg></math>` closed the math. Each element keeps the position of its nearest HTML element, so the check is one comparison.
- **A heading end tag in foreign content matches its name exactly (group 6).** Processed as HTML, it closes the nearest HTML heading of any level. `<h2><svg><h2></h1>` closed the svg. A stack of HTML heading positions makes the lookup constant time even through foreign headings, and popping a heading restores the previous one. Scope boundaries still apply.
- **`svg` inside MathML `annotation-xml` starts an SVG run (group 10),** as the [tree construction dispatcher](https://html.spec.whatwg.org/multipage/parsing.html#tree-construction-dispatcher) sends it to the in-body rules. Its `ms` and `mi` are SVG elements, not integration points, so `<math><annotation-xml><svg><ms><b>` stayed open.
- **Table end tags and `</template>` close through integration points (group 4).** Table scope has no boundaries other than `html`, `table`, and `template`, and `</template>` has none. `<table><math><mo></table>` closed the math. The stack already closed these end tags through every other boundary, so no table insertion mode was needed.

The other groups need parser subsystems that the stack does not have: the form element pointer, the insertion modes for `template` and its contents, the table insertion modes, `nobr` reopening, and the adoption agency algorithm's furthest block. They stay [known gaps](./known-gaps.md) as a deliberate scope limit: each would add code to the bundle for every user, and 0 of the 128 corpus files contain `<![CDATA[`. A later change to the stack compares its fuzz output with the [baseline](./github-oracle.md#baseline). `pnpm bench:ab` against `develop` showed no output difference on its 135 inputs, with timing ratios from 0.94 to 1.01, and the bundle grew by 269 bytes minified and 117 bytes gzip, to 51,806 and 20,190.

This model matches all 34 numbered probes, including probes 9 and 102, which the integration point rules fixed. Elements are tracked only when the source holds `<svg` or `<math`, case-insensitively, because the stack decides nothing else. This check can include text that is not a tag.

An open HTML `select` ignores unrelated start and end tags, including generated paragraph tags. A nested `select` start closes it without opening another; an `input` start closes it and is then processed normally. GitHub /markdown rendered both marker openers in `<div><select></div><svg>` followed by `<!-- a -->PRESERVE <![CDATA[ > <!-- a -->old ]]> tail<!-- /a -->` on 2026-11-15. Thus the ignored `</div>` must not pop the select, and the ignored `<svg>` must not make CDATA foreign. A task-list checkbox is not modeled as a generated `<input>`: for `<select>\n\n- [ ] x <svg>` followed by the same markers, GitHub dropped the list and checkbox markup, kept the select open, and rendered both openers on 2026-11-15, which is what the scanner reports. parse5 instead closes the select at the `<input>`.

**Rejected: follow the standard or a published parser.** parse5, gumbo, lol-html, and libxml2 each disagree with GitHub on several probes ([details](./github-oracle.md#parsers-that-dont-match)). A first implementation ported the standard's foreign-content rules: breakout tags, integration points, and special-element scope. Review found 8 defects in it, several of which made the scanner report a comment where GitHub shows text. Revisit this decision if GitHub's probe results change or a parser that matches them is found. The integration point rules and the implicit close and scope rules above are the parts of that port that GitHub's probes support, each added rule by rule.

## Browser phase

**Browser phase** ([html/tokenizer.ts](../../src/html/tokenizer.ts)). It feeds HTML block lines, raw HTML spans, and, when needed, generated thematic breaks and code blocks through the states of the [HTML tokenizer](https://html.spec.whatwg.org/multipage/parsing.html#tokenization) that decide where a comment starts and ends: data, tags, attribute values, bogus comments, comments, and CDATA sections. It also keeps the stack of open elements that [GitHub HTML handling](#github-html-handling) describes.

## Where a comment ends

A comment ends at the first `-->` that the browser sees. What the browser sees between two raw HTML pieces decides whether an open comment, tag, or attribute value carries across:

- **Within an HTML block,** lines are separated by a line feed only.
- **Between two raw HTML spans in one text block,** the text between them renders escaped, so it holds no `<` or `-->`.
- **Thematic breaks, code blocks, footnote markup, and link, image, autolink, and aligned cell markup** use the generated-output path described above, with its approximations for fence languages and `alt` text, so their bytes can finish an open tag or quoted value. Other generated output still uses the approximations in the [renderer audit](./generated-markup.md#renderer-output-audit): `afterMarkup` treats a write as ending in `>`, while conditional element events approximate its effects on the stack. Open comments, quoted values, and CDATA carry past that approximation. Two adjacent HTML blocks have no generated markup between them, so every state carries.

`<!-->` and `<!--->` end a comment at once, as both CommonMark and the HTML standard specify, and are reported as empty comments. `--!>` ends a comment as `-->` does (`incorrectly-closed-comment`). A comment still open at the end of the document runs to its end (`eof-in-comment`). An HTML block can leave one open, and so can inline raw HTML whose bogus comment ends at an early `>`, as in `# x <![CDATA[ > <!-- ]]>`. An inline `<!--` that cmark-gfm does not read as raw HTML, such as `text <!-- a`, is text.

**Decision (2026-11-16): report comments that end at a parse error.** The scanner used to report only comments closed by `-->`, because the others cannot hold a marker. GitHub still builds them, and a comment that runs to the end hides the rest of the page, which a linter such as mdeval must report. Reporting them follows GitHub; deciding what they mean is the consumer's job. GitHub `/markdown` on 2026-11-16 hid everything after `<!-- a\n\nVISIBLE` and `> <!-- a\n\nVISIBLE`, showed `VISIBLE` after `<!-- a --!>\n\nVISIBLE`, and rendered `x  VISIBLE` for `x <!--> VISIBLE`, `x <!---> VISIBLE`, and `x <!-- a --!> VISIBLE -->` (the last one with ` --&gt;` after it). The fixtures `eof-comment`, `eof-comment-blockquote`, `bang-closer-block`, `empty-comment`, `empty-comment-dash`, and `bang-closer-inline` in the [probe fixtures](./github-oracle.md#probe-fixtures) hold these outputs. [compare.ts](./github-oracle.md#scripts) compares every comment node and its closer kind; on seeds 7, 11, and 23 with 20,000 documents per fragment set, its mismatch counts equal the `-->`-only counts from before this change.

## Where a comment starts its line

`onCommentLine` is `true` for every comment on an HTML block line whose first content, after spaces and tabs, is a comment. The block phase decides what is an HTML block line, and the HTML tokenizer sets the flag, so it follows cmark-gfm's HTML block rules. Checked with `findComments` on 2026-11-17:

- **A comment that opens an HTML block** has at most three columns of indentation after container prefixes, with tabs expanded. Four or more columns at the top level are indented code, where comments are skipped. In a paragraph, they continue the paragraph, so `Before\n    <!-- a -->` is inline and `onCommentLine` is `false`.
- **A comment that begins a later line of an open HTML block,** such as the lines after `<div>`, starts its line at any indentation, because the whole line is raw HTML.
- **Every comment on a line that starts with a comment** shares the value, including adjacent comments such as `<!-- a -->x<!-- /a --><!-- b -->`, and comments after an empty `<!-->`.
- **On the line where a multiline comment closes,** later comments inherit that comment's value: in `<!-- note\n--> <!-- a -->`, both are `true`.
- **A leading byte order mark is not text.** Markdown parsers drop it, so `\uFEFF<!-- a -->` starts its line.
