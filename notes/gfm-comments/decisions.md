# Scanner decisions

These decisions explain why the scanner lives in this package and how its modules are split. The scanning rules themselves are described in [design.md](./design.md), [block-phase.md](./block-phase.md), [inline-and-links.md](./inline-and-links.md), and [html-tokenizer.md](./html-tokenizer.md).

## Publishing and extraction

**Decision (2026-11-16): publish the scanner as gfm-comments.** comment-mark and mdeval both need the comments that GitHub renders, and mdeval gets them today from micromark and parse5 with workarounds where they differ from GitHub. The package reports each comment's offsets, the `nextLinePrefix` editing aid, and `onCommentLine`. It does not pair markers or decide what a comment means. `onCommentLine` cannot be derived by a consumer from the comments it keeps: a marker consumer drops an empty `<!-->`, which still sets it for the rest of its line, and the same `>` or `-` is a container marker on one line and HTML block text on another. On 2026-11-16, the better of two derivations matched the scanner on the 170-file corpus but disagreed on 0 to 443 comments per 20,000-document fuzz set from [compare.ts](./github-oracle.md#scripts).

**Superseded decision (2026-11-13): do not publish the scanner as its own package yet.** It now follows GitHub closely, but it has no confirmed consumer. [mdeval](https://github.com/privatenumber/mdeval) was the candidate. It parses with micromark and GFM tables to find code ranges, and separately with `mdast-util-from-markdown` to find rendered leaks, so a switch would speed up only one of its two parses. Revisit when a consumer needs GitHub-faithful comment or raw HTML positions without a tree, or when mdeval's parse cost is measured to matter. An earlier measurement of the previous scanner, about 270 times faster than micromark on a 10.7 MB input, was not repeated for this one.

**Decision (2026-11-14): keep the scanner in TypeScript, not WebAssembly** as in [es-module-lexer](https://github.com/guybedford/es-module-lexer). The scan is not a measured bottleneck: [corpus and performance](./linear-time.md#corpus-and-performance) gives 227 ms for 39.6 MB, about 44 µs per file. A typical run reads a few files, so Node startup and file I/O take more time than the scan. WebAssembly would also add costs. The module would read the JavaScript string either through a copy in linear memory or through a call into JavaScript, and neither has been measured against the TypeScript scan. The build would need a second language or toolchain, such as C or AssemblyScript, and the oracle scripts would load a compiled artifact. es-module-lexer runs on every module load in bundlers and loaders, where per-call cost matters. Revisit when a profile of a real workload shows the scan as the main cost.

**Decision (2026-11-14): split the block phase only where state is not shared.** The parser state, the line loop, `openBlock`, and the container stack stay in one closure in [block/index.ts](../../src/block/index.ts), as in `blocks.c`, because they share mutable line state: `offset`, `column`, `containers`, `leaf`, and `markup`. Splitting them would pass that state between modules. The scanners whose result depends only on the current line moved out. On Node 26.13.0, Apple M2 Max, with `mitata`, scanning 753 unique `.md` files from comment-mark's `node_modules` (5.0M characters, 310 comments) took 28.2 ms per iteration after the split and 28.1 ms before, at comment-mark `b0709a2`.
