# Linear time and adversarial inputs

Markdown is untrusted input. A document can be written to make a naive scanner rescan the same text, so every phase must stay linear in time and bounded in memory on any input. `tests/specs/scaling.ts` compares adversarial inputs and bounds the ratio of the best wall times.

## Scanner invariants

- **Linearity.** Each phase reads the source in order. A code span closer is found with one forward cursor per run length, and cmark-gfm's limit of 80 backticks per code span bounds the number of lengths. Searches that could rescan, such as the next `-->` or the next closing quote, use [utils/forward-search.ts](../../src/utils/forward-search.ts), which reuses a result until the scan moves past it. After the first rendered [footnote](./footnotes.md#footnotes), segments can go back in the source, so searches read only the current segment and reuse a result within it. The [element stack](./html-tokenizer.md#github-html-handling) finds an end tag's element through a per-name index of stack positions, or a separate index of HTML headings, and pops each element at most once. Long names use nested maps with keys of at most 16,383 code units, avoiding V8's length-only hash for longer strings and avoiding a custom hash's multicollisions. Empty paths are removed as elements close. Unclosed tags can make the stack grow with the document, so its memory is O(n) in the worst case. The scaling tests compare adversarial inputs and bound the ratio of the best wall times. They use `performance.now()`, not `process.cpuUsage()`: process CPU time includes V8's background GC and compiler threads, which made the ratios range from 0.67 to 3.12 for a linear scanner when the full suite ran on 2026-11-15. Wall time gave 1.2 to 2.45 in the same runs.
- **Scaling test timing (2026-11-17).** One helper, `bestTimes` in the [scaling tests](../../tests/specs/scaling.ts), times every ratio test. It alternates the inputs within each round and reverses their order every other round. Each sample repeats the scan until it takes about 5 ms, and the helper keeps each input's best sample. It runs 3 to 10 rounds and starts no new round after 0.5 s. Before, each test timed all attempts on the small input and then all attempts on the large one, 2 to 10 attempts of often under 1 ms each. A burst of load during only the large input's window raised every one of its samples, so `unmatched delimiter openers` once failed at 3.49 against its limit of 3.2. With the helper, five runs of the suite at load averages of 13 to 27 all passed. Ratios of doubled inputs stayed between 1.75 and 2.57, against limits of 3 and 3.2. The long-tag tests measured 4.07 to 4.34 against 5.2, and the nested blank-line test 3.62 to 4.33 against 6. On the unmatched-openers input, samples of 5, 10, and 20 ms gave medians of 2.17, 2.23, and 2.33 in 20 runs each at a load of about 25, so a longer sample does not reduce the ratio. Copies with a known quadratic regression still failed: 7.56 to 8.08 for the long-tag tests and 8.01 for the blank-line test. The aligned-table test failed at 3.99. The suite takes about 16.5 s instead of 9.4 s, because each multi-input test now runs at least 3 alternating rounds per input.
- **The `<svg`/`<math` gate** visits each `<` with one native `indexOf` call. On 2026-11-15, Node 26.13.0, it cost nothing measurable on the 170-file corpus (10.4-11.1 ms against 11.0-11.3 ms without a gate) and 1.3 ms on `'< '.repeat(100000)` (3.4 ms against 2.1 ms). Rejected, measured the same day: lowercasing a copy and then searching for `svg` and `math` (13.4 ms on the corpus, because the copy costs time on every document); searching each case form of `vg` and `th` (14.3 ms, because `th` is common in prose); searching `<s`, `<S`, `<m`, and `<M` (5.5 ms on the dense input, because V8 checks every `<` once per needle). The gate stays linear on any input.

## Unmatched foreign heading end tags (2026-11-17)

**Decision: keep a stack of open HTML heading positions.** A heading end tag in foreign content first looks for an exact foreign name. If that fails, the HTML rule looks for the nearest HTML heading of any level, subject to scope boundaries. The index pushes a position when an HTML heading opens and pops it when that element closes. Foreign headings do not enter the index.

Before this change, the fallback binary-searched the positions for every heading level. For `<div>\n<svg>` followed by `n` repetitions each of `<h2>` and `</h1>` and a trailing `<!-- x -->`, the input grew linearly, but wrapping `Math.floor` counted 10,000, 22,000, 48,000, and 104,000 search steps for `n` = 1,000, 2,000, 4,000, and 8,000. The indexed lookup takes constant time per end tag and makes no binary-search steps on that input.

The [scaling test](../../tests/specs/scaling.ts) compares two 1,080,021-character inputs with 20,000 nested foreign elements and 200,000 unmatched end tags. One has five foreign headings; the other has 20,000. On Node 26.13.0 and Apple M5, the test rejected the binary-search version in all three retries, with ratios of 1.57, 1.54, and 1.57 against its 1.35 limit. The same timing helper measured ratios of 1.04 to 1.10 for the index in four runs. This test catches the observed regression, not every possible superlinear implementation. The [stack oracle](./github-oracle.md#element-stack-fuzz) produced byte-identical results to the binary-search version across its three default million-document seeds.

An alternative stored the nearest HTML heading on every element, inheriting it from the parent when the element was not an HTML heading. A 300-round paired A/B run compared that variant with the separate index: the candidate/base ratio was 0.997 on the corpus and 1.009 on a 140,021-character synthetic input, with 0 of 136 outputs different. The synthetic input was `<div>\n<svg>`, 2,000 repetitions of `<h2><h3><h4><h5><h6>`, 20,000 repetitions of `</h1>`, and a trailing `<!-- x -->`. In one retained-heap sample after `global.gc()`, an SVG followed by 300,000 foreign `<ab>` elements used 44.6 MB with the per-element field and 42.2 MB with the index. The index avoids the field on non-headings while keeping the same asymptotic stack bound.

Against the binary-search version, 300 alternating rounds on the synthetic input in isolation gave median times of 17.72 ms before and 6.00 ms after, with a median paired ratio of 0.336. `pnpm bench:ab -- origin/develop . --rounds=300 --warmup=10` measured a corpus ratio of 1.000 and 0 of 135 outputs different.

The synthetic input was not kept in the fixed A/B suite: in separate runs that included it, the ratio on the unrelated `comment-dense` workload ranged from 0.709 to 1.487, against 1.019 before it was added. The scaling test compares the heading workload separately. These measurements do not establish the cause of the unrelated timing swings.

## Early stop after the last comment opener (2026-11-17)

**Decision: the block phase stops after the last `<!--` once no pending state can change a comment.** A comment starts with `<!--`, so the last occurrence of that text is an upper bound on where a new one can begin. `findComments` finds that position once and returns when it is absent, then passes it to `scanDocument`, which no longer searches for it again. Otherwise, `lexBlocks` receives one optional `stop` argument with `after` set to that position and a `canStop` predicate. Giving them together means a caller cannot stop on a position without a predicate, or the reverse. The phase stops after the first line that starts past `after` when all of these hold:

- **No event is held and no reference lookup is deferred.** `buffering` is false. A text block with `[` and `]` outside a footnote definition starts buffering before it is lexed, so while buffering is false, no later definition can resolve a reference that was already lexed. A block inside a definition does not start it, but the next condition already blocks the stop.
- **No footnote definition was seen.** A later reference could render one, replay its events after the rest, and change both the order of its comments and the definition boundaries that split comments.
- **No comment is open in the tokenizer.** Otherwise text after the last opener can still end it, and stopping would report a different end. `inComment()` checks only `state === State.Comment`. Tag, attribute, CDATA, and bogus-comment states do not block the stop: none of them reports a range, and text after the last opener cannot start a comment, so ending them changes no result. An earlier version waited for the data state through `wantsCode()`.
- **No paragraph or heading that began at or before the opener is open.** Their text has not reached the tokenizer, so the comment-state check cannot see an unclosed `<!--` in them. Cutting them at the stop could remove their closer. A paragraph or heading that began after the opener cannot hold one. Code blocks render escaped and HTML block lines are fed as they are read, so those leaves need no wait.

Any condition that cannot be proven safe keeps the phase running. The last condition is stricter than the audit's description, which named the held-event and tokenizer conditions but not the open text leaf. It is needed because `finalizeLeaf` sends a paragraph's text to the tokenizer after the block phase decides to stop.

The loop reads one line per iteration, including a final line without a line ending, and a stop breaks out before the remainder. `processLine`, and the `readTableRow` and `HtmlTokenizer.feed` work it drives, read one line whose end is `lineEnd`, and every call now satisfies that by construction. An earlier version made a separate final call after a stop and passed the remainder as one line, which put interior line endings in that range. A test that runs `lexBlocks` directly and asserts every reported range stays within one line locks the contract.

The tail after the loop still runs for a stopped document. `finalizeLeaf` closes the open leaf: it cannot be a paragraph or heading that began at or before the opener, so its text holds no `<!--`; code blocks render escaped, and HTML block lines were already fed. `popContainer` then emits only closing container markup, and no footnote container can close because any definition would have kept the phase running. No comment is open in the tokenizer, so `finish` reports no comment from the closing markup.

The boundary cases are locked by [early-exit.ts](../../tests/specs/rendering/early-exit.ts): a reference definition after the last opener that resolves an earlier image, an open footnote definition whose comment closes after it, a footnote comment whose closer is on a later line, an HTML attribute opened before it whose comment closes after it, and a tag or attribute left open after it, where the phase stops.

The stop also applies to the [scaling tests](../../tests/specs/scaling.ts), so each measured payload must end with a comment or share a paragraph with one. Seven tests put their only comment before the payload and stopped after their first line: the two long-tag tests, the four open-attribute-value tests, and the `x <svg>\n\ntext\n\n` foreign-content input. They passed without measuring anything. On 2026-11-17, a trailing comment fixed them:

- Lookups of 16,383-character chunk keys, counted by wrapping `Map.prototype.get`, went from 0 to 512 for 512 long tags.
- With the trailing comment, the long-tag tests compare 512 with 2,048 names, because doubling separated a quadratic stack poorly. Two quadratic copies were measured. One kept whole names as `Map` keys, so V8 hashed them by length only. The other kept long names in a list compared with `===`, as if every name had the same hash. They measured 7.4 to 8.2, the scanner 3.8 to 4.0, and the limit is 5.2. At 512 and 1,024 names, the colliding test measured 2.5 for both copies, under its limit of 2.6.
- A copy that writes every generated empty aligned cell measured 3.97 on the aligned-table input with the trailing comment, and 0.1 ms for any size without it.

Measured on the 1,882,743-character corpus with `pnpm bench:ab -- develop . --rounds=300` against `develop` as of the [cleanup](./performance.md#cleanup-2026-11-17), with the hoisted closures and first-character guards applied: two clean runs measured corpus ratios 0.818 and 0.820, with 0 of 135 outputs differing. The loop restructure kept the ratio at those numbers, against 0.819 and 0.812 before it. A third run measured 0.831 while inflating every small synthetic workload. About 23.3% of the corpus characters lie after the last `<!--`; the audit's prototype skipped 12.9% of them, and this stop keeps the output identical on the default fuzz seeds and on seeds 1, 2, 3, and 5.

## Blank lines in nested containers (2026-11-17)

**Decision: on a line with nothing left to read, `check_open_blocks` jumps to the next container that can stop the line.** cmark-gfm visits every open container on every line ([`check_open_blocks`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L1052-L1116)). On a non-blank line that is linear, because every container except a list consumes at least one column, and a character holds at most four columns. On a blank line it is not: a list, a list item with a child, and a footnote definition on an empty line continue without consuming anything. Nested definitions or list items followed by many blank lines cost depth × lines, so a 107,737-character document took 1.6 s: 16 lines of nested footnote definitions, each indented 396 spaces more than the last and holding 99 `[^a]: ` markers, then 50,688 newlines and `<!-- x -->`.

Once `offset` reaches the line end, the rest of the loop changes no state: `findFirstNonspace` gives an indent of 0, and `advance` is called with 0. Each remaining container then only decides whether the line stops on it:

- A blockquote stops it, because no `>` remains.
- A footnote definition stops it unless the line is empty, because its indent of 0 is less than 4.
- A list item stops it only without a child. Every container is pushed through `addChild`, which marks a list item parent as having a child, so only the innermost container can be an item without one.
- A list never stops it.

So `matched` is the smallest of the next blockquote, the next footnote definition on a non-empty line, and the last container, where the normal loop body decides. `lexBlocks` keeps the indices of the open blockquotes and footnote definitions in two stacks, pushed and popped with their containers. The loop counts the blockquotes and footnote definitions it continued, and these counts index the next of each. A blockquote can come before the jump, on a line such as `>`, so the count is needed for blockquotes too.

The jump gives the same `matched` as the original loop and leaves the line state the same, so the result is identical. Evidence, with Node 26.13.0:

- `node scripts/oracle/compare.ts --show 1000` output is byte-identical to `develop` before the fix.
- A differential harness compared every `lexBlocks` event and every `findComments` result with `develop` on 200,000 random documents, built from 1 to 12 lines of up to 6 pieces such as `> `, `- `, `1. `, `[^a]: `, spaces, tabs, a byte order mark, fences, and table rows, with LF, CRLF, and CR endings. All matched. The same harness found differences for two wrong versions: one that took the first open blockquote instead of the next one, and one that took the first open footnote definition.
- That document and its 28,529-character version with 8 lines and 12,672 newlines went from 1.64 s and 217 ms to 7.7 ms and 2.6 ms. Nested list items followed by empty lines, or by lines of one space, behaved the same way before the fix: 1.8 s and 0.9 s at about 78,000 characters, and 4.9 ms and 3.7 ms after it.

Footnote definitions followed by lines of spaces were already linear, because a definition consumes 4 columns or stops the line. Nested blockquotes stop on any blank line. The [scaling test](../../tests/specs/scaling.ts) for blank lines in nested containers measured a ratio of about 8.1 before the fix and about 3 after it, for about 3.8 times more source.

## Corpus and performance

The corpus is 5,141 unique `.md` files (39.6 MB, 2,769 comments) from a local `node_modules` tree. Against comment-mark `develop` at `5723ed5`, every comment start, inner range, and next-line prefix is the same. 20 files differ only in the `onCommentLine` flag, because a comment that begins a later line of an HTML block now starts its line at any indentation.

Scanning the whole corpus as one string with `mitata` on an Apple M2 Max: this scanner 227 ms per iteration, `develop` 392 ms. Both find 2,769 comments.

**Links and references (2026-11-14).** Measured on a 758-file sample of the corpus (5.5 million characters, 309 comments), scanning each file separately, as a consumer reads documents one at a time. An earlier harness joined the files into one string, which hid per-call costs and sent the whole sample down the reference budget's slow path. On the 170 files that contain `<!--`, link, reference, and table-cell handling costs 7 to 12% against comment-mark `develop` at `afdc279` in three paired runs, for example 10.7 ms against 9.7 ms. Over all 758 files, the scan takes 10.9 ms against 28.8 ms, because files without `<!--` now return at once. A first version ran a second block pass to collect labels on every document, and it took about twice as long as base. Peak RSS with `/usr/bin/time -l` is unchanged from comment-mark `afdc279`, about 96 MB, for 500,000 HTML block lines after one marker, and about 94 MB for a 1 MB unclosed link destination. Those inputs measured 174 MB and 126 MB before events were streamed and the destination index was built lazily.

**Emphasis follow-up (2026-11-15).** With Node 26.13.0 and `mitata` on the same machine, two paired runs scanned the 170 comment-containing corpus files individually, totaling 1.4 million characters. The supplied `snap-a` scanner took 11.12 and 10.99 ms per iteration; comment-mark `f3d5106` took 14.04 and 13.30 ms. Each found 309 comments. `snap-a` differs from the immediate parent, so this is not a parent comparison. In a separate synthetic corpus with `\n<svg/>` appended to each file, the actual parent in comment-mark, `5e3ae02`, took 16.17 and 16.47 ms, and comment-mark `f3d5106` took 16.10 and 16.86 ms. Each again found 309 comments. The synthetic input exercises foreign-content tracking in every file; it is not representative of the unmodified corpus.

**Generated blocks (2026-11-15).** With Node 26.13.0 and `mitata` on the Apple M2 Max, two paired runs scanned the same 170 comment-containing files individually, totaling 1.4 million characters. The parent in comment-mark, `8872f1e`, took 10.89 and 10.59 ms per iteration; comment-mark `2d57a1d` took 10.89 and 10.91 ms. Each of the four measurements found 309 comments.

**Footnotes (2026-11-16).** With Node 26.13.0, a harness scanned the 128 unique corpus files that contain `<!--` individually and took the best of 150 iterations, in 4 separate processes per scanner, alternating between them. The system load was 9 to 11. The scanner before the footnote change took 10.79 to 11.03 ms, and the footnote scanner 11.13 to 11.26 ms, about 3% more. On the 124 files without `[^`, a split run of 3 processes each gave 10.50 to 10.75 ms against 10.63 to 10.75 ms. Run-to-run noise was about 0.2 ms. Ablation and CPU profiles spread the rest of the cost over the block phase, the inline lexer, and the `[^` lookahead, with no single source above 0.15 ms. Three changes that each looked cheaper measured slower and were not kept: a check of the block for `[^`, `[\`, or `[&` before the lookahead, the same check after `hasBrackets`, and one flag for `synthetic || unordered` in the tokenizer's search. A run with 16,000 comments in one footnote definition line took 3.7 ms. Before the tokenizer reused segment search results, it took 4.9 s, because each comment searched for `--!>` to the end of the line.

**Profile-driven fixes (2026-11-16).** A `node --cpu-prof` profile of 128 comment-containing `node_modules` files (1.88 million characters, 264 comments) on Node 26.13.0 put 79% of busy time in the block phase. Per-file timing found one outlier: the Node.js runtime README ran at 28 ns per character against 6 to 9 for the others. Its `<<name@example.com>>` lines contain `<math`, which enables foreign-content tracking, so every list paragraph goes through the inline phase. Four fixes followed. Each number is the minimum of many runs in separate processes against `develop` before these fixes, measured at load averages from 5 to 12:

- **Emphasis buckets.** `Array.from({ length })` was a quarter of that README's scan time, with or without a mapping callback. Stacks linked through each delimiter, held in two small array literals per call, raised the throughput from about 1,500 to about 2,250 scans per 2 seconds. Reusing the arrays across calls was about 4% slower and needed an invariant that every call empties them. `new Array(n).fill()` was as fast as literals, but lint forbids it.
- **Table rows.** Matching a table line and then opening its row read the row twice. Holding the row for the rest of the line took 200,000 rows from 82 ms to 72 ms.
- **Definition line counts.** Counting line feeds with `indexOf` instead of reading every character took 100,000 definitions from about 72 ms to 63 ms.
- **Label colon gate.** A definition's label and colon share one line, so a paragraph without `]:` is not joined and parsed. This took 50,000 link-led paragraphs from 28 ms to 22 ms. A forward search keeps the gate linear, because paragraphs close in source order.

Together, the corpus went from 11.6-11.9 ms to 10.7-11.1 ms. 300,000 HTML block lines stayed at about 42 ms, and peak RSS stayed at about 101-103 MB.

**Link and cell markup (2026-11-16).** With Node 26.13.0, the harness above took the best of many scans of the 128 corpus files with `<!--` in 4 processes per scanner, alternating between them, at load averages of 4.7 to 5.2. `develop` before the link and cell markup change took 11.11 to 11.29 ms, and the [link and cell markup](./inline-and-links.md#link-image-and-cell-markup) scanner 11.20 to 11.37 ms, 0.8% more in the minimum. A second harness alternates both scanners in one process and takes the median of the per-round time ratios. It gave 1.005, 1.007, and 1.014 in three runs of 400 rounds, where repeat runs of one scanner differ by about 1%. A counting copy showed that the scanner renders no link markup on the corpus. A first version that treated every held HTML line or raw HTML block as able to leave the data state measured 1.023 to 1.033. Per-file timing put the cost in rule-list READMEs whose aligned tables follow a held `<sup>` or marker comment, such as eslint-plugin-react's (17% slower), and the narrower `heldLeavesData` rule removed it: the per-file totals went from 1.031 to 0.997 of `develop`.

The [scaling tests](../../tests/specs/scaling.ts) compare the time for 3,000 and 6,000 repetitions of unmatched openers, long runs, and alternating `*_`, with `<svg/>` present. In an isolated scanner copy, each test rejected a quadratic mutation: repeated backward opener searches, rescanning the remaining long run per match, and rescanning the prefix per alternating delimiter. Their measured ratios were 3.88, 3.91, and 3.92 against a limit of 3.2. These mutations demonstrate those failure modes, not detection of every possible performance regression.

Scaling: each adversarial input below was scanned at 20,000 and 40,000 repetitions, and the time ratio stayed at or below 2: repeated definitions and failing definitions, long labels and escaped titles, open comments, backtick runs, open attribute values, table rows, HTML blocks, nested lists, `< ` and `<!` runs. The [scaling tests](../../tests/specs/scaling.ts) also cover unclosed link destinations and brackets, many references and definitions, and long labels. Since 2026-11-16, they also cover link, image, and autolink markup and aligned table cells in an open single-quoted value, where all of it is rendered: links, images, and autolinks in one paragraph, links in an unclosed bracket, many paragraphs of links without raw HTML, and short rows of a wide aligned table. A copy that writes every generated empty aligned cell failed the last test, at 25 s.
