# Footnotes

GitHub renders with cmark-gfm's footnote option. The renderer moves each referenced definition to the end of the page and drops unreferenced definitions, so a comment's position in the source can differ from its position in the output. This file records the model and its cost.

**Decision (2026-11-16): model footnotes as GitHub renders them.** The renderer moves each referenced definition to a `<section class="footnotes">` list at the end of the document, in the order of first reference, and drops every unreferenced definition ([`process_footnotes`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L465-L545)). Before this decision, the scanner read a definition as a paragraph. It reported the comment in `[^a]: A <!-- c --> B`, which GitHub drops (probe 14 below), and it missed the quotes that generated footnote markup writes, which can close an open attribute value (probe 12).

The model has four parts:

- **Block phase.** A definition `[^label]:` opens a container, as [`open_new_blocks`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L1218-L1236) does: after the thematic break check, below the list depth limit, and only at a `[`. A later line continues the definition when it is indented 4 or more columns, which the container consumes, or when the line is literally empty ([`parse_footnote_definition_block_prefix`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L929-L939)). A line of spaces ends it. An empty line ending in a lone CR continues it, because cmark-gfm replaces every line ending with `\n` before the check ([`S_process_line`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L1468-L1470)). Comments that start a line in a definition get the next-line prefix `'    '`. Each definition is a separate output stream with its own `markup` flag, which is saved when it opens and restored when it closes. The phase also records whether the definition's last child is a paragraph, because the renderer then writes the backlinks inside that `<p>` instead of after it. A thematic break is not a leaf, but it can be the last child, so it clears that flag: for `x[^a]\n\n[^a]: A\n\n    ***`, cmark-gfm writes `<hr />\n<a …>↩</a>`. No test locks this, because no comment depends on it. In Data state only the element changes of generated markup apply, and the backlink holds the same quotes in both forms.
- **Labels.** Definitions register as they close, and the first definition of a normalized label wins. Any bracket whose text starts with `^`, and that does not become a link, is a reference, defined or not ([`noMatch`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/inlines.c#L1236-L1314)). An escaped `\^` or an entity such as `&Hat;` also starts one (probe 9). A reference drops the inlines inside its brackets, so a comment there never renders (probes 1 and 6). Its label is the decoded text after the caret up to the first inline that is not text: a line ending, hard break, code span, autolink, raw HTML, completed inner link, image, or footnote reference (probes 1, 4, 5, 7, 8, 13, and 15). Emphasis delimiters stay in the label (probe 4). cmark-gfm 0.29.0.gfm.13 instead copies the source columns between the brackets from the first text node's buffer, which reads past that node when an inline or a decoded entity is in between. GitHub's output follows the text rule, so the local oracle disagrees on such documents, and with `&Hat;` its output can be truncated.
- **Numbering.** A counting pass, the reference budget's second pass, walks every text block in document order and numbers each definition at its first reference. References count wherever they stay in the tree, including inside unreferenced definitions (probes 2 and 3) and image descriptions (probe 16), but not inside an outer reference (probe 15).
- **Replay.** Definition events are held per definition. After the body, each rendered definition replays between the renderer's exact head and tail markup: `<section class="footnotes" data-footnotes>\n<ol>\n<li id="fn-…">` for the first one, and the `data-footnote-backref` links in the tail. The end writes `</ol>\n</section>`. A reference writes `<sup class="footnote-ref"><a href="#fn-…" id="fnref-…" data-footnote-ref>N</a></sup>`. These go through the tokenizer's generated-markup path, so in Data state only their element changes apply. The label is escaped as `houdini_escape_href` escapes it, so it holds no quote, `<`, `>`, or whitespace and cannot change the tokenizer's state. The `-N` suffix on the second and later references to one definition counts in replay order, which can differ from document order, but its digits cannot change the tokenizer's state either.

**Decision (2026-11-17): brackets in a definition do not hold the main document.** A text block with brackets starts main-document buffering, so a later definition can still resolve its references. Before this change, a block inside a footnote definition started it too, and every later main-document event was held until the end, although the definition's events are already held in its own list. A main-document event can depend on labels only when it has brackets itself, and then it starts buffering. The other readers of `buffering` stay correct. References inside the definition, including an unreferenced one, still count toward other footnotes, because the reference budget lexes the source again in its own pass, and any definition makes that pass run. The early stop already waits for any footnote definition. `heldLeavesData` matters only while main events are held. Returned comments do not change, so no test can observe the difference through `findComments`, and the footnote and reference tests lock the outputs. With `mitata` on Node 26.13.0, the reproduction, `[^a]: [r]\n\n` followed by `---\n\n` repeated 50,000 times and `<!-- x -->`, went from 12.5 MB to 5.3 MB of estimated heap per iteration, the same as the case without a closing bracket, `[^a]: [r \n\n`.

**Decision (2026-11-17): the tail writes at most two backlinks.** The renderer writes one backlink per reference, which is n log n characters for n references, while each reference in the source has constant length. Outside the data state the tokenizer read all of them: `[^a] ` repeated 80,000 times before `[^a]: <div title='` built a 15.2-million-character tail. Writing only the first two backlinks gives the same tokenizer state and element stack, so no comment changes:

- A comment, single-quoted value, or CDATA section stays open through every backlink, because no backlink holds `-->`, `--!>`, `'`, or `]]>`. The label is escaped by `houdini_escape_href`, so it holds none of them either.
- From any other state, the first backlink ends in the data state: its first `"` ends a double-quoted value, and a `>` ends any tag or bogus comment.
- From the data state, a numbered backlink opens `a` and `sup` and then closes `sup` and `a`. Neither is an integration point, so each end tag pops the element its start tag pushed, and the stack is unchanged.
- Backlinks after the second differ from it only in digits, which change no transition.

A temporary probe of the tokenizer's state and stack, run from 20 start states including SVG, MathML, `foreignObject`, and `select` contexts, gave the same result for 2 to 5 references. With `mitata` on Node 26.13.0, the 80,000-reference reproduction in #4 went from 69.4 ms to 22.8 ms per iteration in the open case, against 21 ms for the closed case before and after. A test in [scaling.ts](../../tests/specs/scaling.ts) compares the two cases at 40,000 references; it measured a ratio of 1.88 before the change against a limit of 1.5. Rejected: feeding backlinks one at a time until the state stops changing. It needs a new tokenizer entry point and a state comparison, and the argument above shows that the second backlink is always that point.

**Decision (2026-11-16): reported ranges are disjoint and in source order.** Consumers apply replacements from the last comment to the first, which is safe only if no range holds another. From the first definition on, the scanner holds the comments it finds and sorts them by start before it reports them. After the first rendered definition, segments go back in the source, so the tokenizer searches only within the current segment and keeps each result for that segment. Each character is still read a bounded number of times per needle.

A comment's range never crosses the source start or end of a rendered definition. A definition's source range runs from its `[^` to the start of the first line that does not continue it, or to the end of the source. The scanner first finds each comment's natural end: its closer, or `source.length` for a comment that is still open when its stream ends. If a rendered definition's start or end lies after the comment's opening and before that natural end, the first such boundary becomes both `contentEnd` and `end`, so the closer is empty. A sorted list of boundaries and one forward pointer over the sorted comments do this, only when a definition exists. The rule has three consequences:

- **A comment left open in a footnote** ends with its definition, as in `x[^a]\n\n[^a]: A\n    <!-- open\n\nBODY <!-- z -->`. `BODY` is visible on GitHub, so a range to the end of the document would hold it and the reported `<!-- z -->`. Probe 11 is the case where the next stream is another footnote.
- **A body comment that spans a rendered definition** ends at the definition's start, as in `<div>\n<!-- open\n\n[^a]: VISIBLE\n\n<div>\n-->\n\nx[^a]`. GitHub closes it at the `-->` after the definition, but it moves `VISIBLE` to the end of the page, so replacing the true range would delete footnote text that GitHub shows. The body comment that runs into the footnote list (probe 10) is unchanged: it starts after the last definition and runs to the end of the document.
- **An unreferenced definition** renders nothing, and none of its comments are reported, so a range across it keeps its true closer, as in `<div>\n<!-- open\n\n[^b]: A\n\n<div>\n--> B`.

An empty closer therefore means that GitHub does not close the comment within this stretch of source: it runs to the end of the document or of a footnote definition, or up to a footnote definition that GitHub moves.

The clipped range can be shorter than what GitHub hides. In the `VISIBLE` example, GitHub also hides the `<div>` line after the definition, which is not in any reported range. Splitting the comment into two ranges was not chosen, because the second part would not start with `<!--`.

**Cost.** Some footnote code runs on every document, with or without a definition. The block phase's `finalizeLeaf`, `popContainer`, and continuation check each test for an open footnote container. A text block without raw HTML is lexed only when its markup can meet a state other than data, which `mayLeaveData()` decides; see [Link, image, and cell markup](./inline-and-links.md#link-image-and-cell-markup). Every block with brackets now qualifies, and every footnote reference has brackets, so the search for `[^` that once decided this was removed on 2026-11-16. The inline phase calls `scanCaret` at every `[` to test for a caret. A precheck of the whole source with `includes('[^')` would avoid the search, but it cost 0.33 ms on the 124 corpus files with `<!--` and without `[^` (1.8 million characters, 2026-11-16, Node 26.13.0), about 3%. Small branches in the per-line block closures cost about 0.25 ms each, a V8 inlining effect found by ablation, so the footnote branches stay few and short. Replay, the per-segment searches, and the sorting and clipping of results run only when a definition exists.

**Behavior change without `[^`.** An escaped caret or an entity, as in `[\^a]` and `[&Hat;a]`, also starts a reference (probe 9). Such a bracket now drops its inlines and renders reference markup, so it can change which comments are reported in a document that has no literal `[^`. This follows GitHub.

Probe 6 overturned an earlier inference that an undefined reference keeps its inlines as text. The [footnote tests](../../tests/specs/rendering/footnotes.ts) lock one case per rule; each case was checked against the oracle or a probe. Two cases, where the list head or a backlink closes an open attribute, fail on the scanner before this change and pass after it.

**Rejected: a precheck for `[^` before the scan.** It is simpler, but it scans every document in full and cost about 3%; see Cost above.
