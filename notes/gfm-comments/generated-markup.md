# Generated markup

The renderer writes HTML around Markdown nodes as well as copying raw HTML from the source. The scanner writes the markup that can change an HTML tokenizer state, and approximates the rest. This file covers the exact writes, the renderer-output audit, and the rejected alternative of replaying every write.

## Generated thematic breaks and code blocks

The renderer writes `<hr />` for a thematic break and `<pre><code>` around fenced or indented code. With `--github-pre-lang`, a language produces `<pre lang="..."><code>` ([`html.c`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/html.c#L215-L254)). The block phase sends the tokenizer an event in renderer order. If the tokenizer is in Data state after preceding markup, it skips rendering and, when tracking foreign content, applies the code block's `pre` and `code` element transitions. In other states, [render/code-block.ts](../../src/render/code-block.ts) renders the block and the tokenizer reads that synthetic HTML as decoded text, except that a named entity value in a fence language keeps its first byte when that byte is ASCII and writes U+FFFD for the rest, while a name the [entity table](./reference-budget.md#reference-expansion-budget) does not hold stays as its source text. Neither form can end the quoted attribute. The preceding conditional line feed still uses the tokenizer's boundary approximation; the exact-output path does not reconstruct earlier writes. Synthetic searches do not advance source searches, and a comment is reported only when both endpoints are in the original source.

cmark-gfm decodes entities in a fence's info string, trims it, and removes backslash escapes before the renderer selects its first whitespace-delimited language. Its block parser replaces a partially consumed tab with spaces and removes trailing blank lines from indented code ([`blocks.c`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L207-L248), [finalization](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L326-L350)). The generated-block renderer follows those rules and escapes `&`, `<`, `>`, and `"`. The [generated block markup tests](../../tests/specs/rendering/generated-block-markup.ts) cover these details, source-only comment ranges, and both streamed and buffered events.

When a code block needs to be retained for replay, the block phase stores one source start offset per line and separate `[lineIndex, spaces]` pairs only for partially consumed tabs. Indented code trims both arrays after the last nonblank line. The renderer scans from each offset to the next CR or LF: cmark's [`add_line`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L207-L221) appends from the container-adjusted offset to the end of the line for either code block kind, and its [input loop](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/blocks.c#L714-L783) normalizes CR, LF, and CRLF. On Node 26.13.0 on macOS, scanning ```` '[x] <!-- a -->\n\n```\n' + 'x\n'.repeat(1_000_000) + '```\n' ```` with `findComments(source)` and reading `process.resourceUsage().maxRSS` used 233,232 KiB with three numbers per line, 156,320 KiB with this representation, and 104,672 KiB on the earlier autolink scanner. These are single-run peak RSS measurements, not retained heap measurements.

On 2026-11-15, GitHub `/markdown` confirmed that both marker openers render after `'<div>\n<svg\n\n---\n\n'` and after `'<div>\n<pre><svg\n\n```\nx\n```\n\n'`, followed by `<!-- a -->PRESERVE <![CDATA[ > <!-- a -->old ]]> tail<!-- /a -->`. The [foreign content tests](../../tests/specs/rendering/foreign-content.ts) (lines 27-49) preserve `PRESERVE` and replace the later marker's content. A GitHub probe on the same day confirmed that only the outer opener renders after `'<div>\n<svg\n\n```js\nx\n```\n\n'`; `lang="js"` completes the unfinished SVG tag without self-closing it. That test also passes on the parent. parse5 predicts differently because it breaks out of SVG at `<code>`. The fixtures `hr-completes-tag`, `pre-completes-tag`, and `pre-lang-keeps-svg` in the [probe fixtures](./github-oracle.md#probe-fixtures) hold these three probes.

## Renderer output audit

The following audit covers every output branch in cmark-gfm 0.29.0.gfm.13's [`html.c`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/html.c) and the five enabled extensions. The local oracle uses `CMARK_OPT_UNSAFE`, `CMARK_OPT_GITHUB_PRE_LANG` (`--github-pre-lang`), and `CMARK_OPT_FOOTNOTES`; that is not an independently verified list of all GitHub renderer options. Source-position attributes, `FULL_INFO_STRING`, `HARDBREAKS`, `NOBREAKS`, and table style attributes are not enabled in that oracle. `cmark_html_render_cr` conditionally inserts a line feed; `cmark_html_render_sourcepos` writes a quoted attribute only when its option is set ([`html.h`](https://github.com/github/cmark-gfm/blob/0.29.0.gfm.13/src/html.h#L8-L23)).

**Current** distinguishes exact synthetic output from approximations. `afterMarkup` approximates an intervening write, and `open`/`close` also model element transitions when foreign-content tracking is enabled. Some inline writes are not reported at all. **To make exact** lists what exact output would still need. It is not planned work: see [Rejected: exact replay of every write](#rejected-exact-replay-of-every-write).

### Rejected: exact replay of every write

On 2026-11-15, a prototype passed the exact generated string for every write in this audit to the tokenizer, and removed `afterMarkup`, `open`, and `close`. It passed every test and fixed 22 of the 29 `tables` fuzz mismatches, but it was rejected:

- **Cost.** With tracking off, it took 45.7 and 74.5 ms on the 170-file corpus, against 10.9 and 10.7 ms for comment-mark `8872f1e` (Node 26.13.0, two paired runs, 309 comments each). Rendering every write costs time on every document, while the writes matter only after raw HTML leaves a tag, attribute value, or bogus comment open.
- **Size.** It added about 2,200 lines, including a second document walk for list tightness.
- **Fidelity.** The [task-list probes](./github-oracle.md#task-list-checkbox-and-attribute-boundary) show that replaying cmark's `<input>` would make the scanner worse. An archived filter supports post-parse insertion as an inference, not a confirmed current pipeline.

Only code blocks, thematic breaks, footnote markup, and [links, images, autolinks, and aligned cells](./inline-and-links.md#link-image-and-cell-markup) are rendered, and only when the tokenizer is outside Data state. Their output is exact except for a named entity value in a fence language, which keeps its ASCII first byte and replaces the rest with U+FFFD, or stays as escaped source text when the entity table does not hold the name, and an image's `alt` text, which is empty. Evaluate this again for one write at a time, when a GitHub-confirmed issue needs it and the write can be rendered lazily, as code blocks are. The link and cell markup followed this rule on 2026-11-16: GitHub probes confirmed each write, and it cost no measurable time on the corpus.
